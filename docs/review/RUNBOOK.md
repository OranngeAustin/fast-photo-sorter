# 自动审查与优化手册（给 Claude 执行）

## 工作规则
- 无人值守运行：不要向我提问，也不要等待确认。需要决策时选最保守、可回退的做法，
  并把决定和理由写进 docs/review/PROGRESS.md 的「决策记录」。
- 每完成一个阶段或一个子任务，立即更新 PROGRESS.md 并提交推送（跟随当前分支提交即可）。
- 每个阶段结束时，在回复里用一两句话报告进度：哪些阶段已完成、下一步做什么。
- 上下文被压缩后，先重新阅读本文件和 PROGRESS.md，再继续。
- 禁止：推送到 main、force push、合并任何 PR、删除分支。
- 不改对外接口、数据库结构、生产配置；不升级依赖的大版本。
- 跳过 CLAUDE.md 中列为忽略的目录。
- 每次改代码后运行测试。测试不通过就修复或回退该改动；
  不允许为了通过测试而修改或删除已有测试的断言。
- 同一任务连续 3 次尝试失败：回退该任务的改动，在 PROGRESS.md 记为「⏭ 跳过」并写明原因，继续下一项。

## 阶段 0：准备
1. 安装依赖，运行全部测试和基准测试（如有），把结果作为基线写进 PROGRESS.md。
2. 已有的失败测试只记录、不修；之后以「失败数不增加」为标准。
3. 从 main 创建分支 claude/review-fixes。
4. 创建 docs/review/PROGRESS.md，列出阶段 0 到 7 的清单。

## 阶段 1：架构摸底
阅读整个仓库，写 docs/review/01-architecture.md：模块划分、入口、核心数据流、
外部依赖、高风险区域，以及按风险从高到低的审查顺序（精确到目录）。

## 阶段 2：代码审查
按阶段 1 的顺序逐个目录审查（使用 code-reviewer 子代理或 /code-review），
结果写入 docs/review/02-findings.md：
- 按 高 / 中 / 低 分组，每条含：编号（如 H1、M3）、文件:行号、问题、原因、修复建议、把握程度
- 不确定的问题单独列在「待人工确认」

## 阶段 3：安全审计
对全仓库检查：注入（SQL / 命令 / 模板）、鉴权与越权、敏感信息硬编码或写入日志、
不安全的反序列化、依赖中已知的高危版本。结果追加到 02-findings.md 的「安全」一节，编号接续。

## 阶段 4：修复高危问题
在 claude/review-fixes 分支上，只修复「高」级别且把握较大的问题：
- 每个问题一个 commit，提交信息引用发现编号
- 每次修复后运行测试
- 完成后推送分支，创建指向 main 的 PR，描述里列出修复清单和测试结果

## 阶段 5：性能分析
运行性能分析和基准测试，分析热点函数的复杂度，写 docs/review/03-perf-plan.md：
- 每个热点：位置、当前复杂度、耗时 / 内存数据、优化方案、预计收益、风险
- 按「收益高、风险低」排序，选前 3 项进入阶段 6

## 阶段 6：算法优化（对选中的每一项重复）
1. 从 claude/review-fixes 创建分支 claude/perf-<简短名称>
2. 相关函数测试不足时，先补特征测试，固定当前的输入输出行为，单独 commit
3. 写或完善基准测试，运行 5 次取中位数作为基线
4. 实施优化，目标：基准中位数提升 20% 以上且全部测试通过。
   最多尝试 3 种方案；达不到就保留最好的正确版本；提升不到 5% 则放弃并回退
5. 做一次清理（复用已有函数、去掉冗余，可使用 /simplify）
6. 推送分支，创建 PR，目标分支设为 claude/review-fixes，
   描述里附前后对比表（耗时、内存、复杂度）
注意：云端计时有波动，只比较相对提升。

## 阶段 7：总结
写 docs/review/00-SUMMARY.md：完成了什么、所有 PR 链接、跳过项及原因、
「待人工确认」的问题、建议我下一步做什么。
确保最终版 PROGRESS.md 和 00-SUMMARY.md 都在 claude/review-fixes 分支上并已推送。
